Kubernetes CSI

This appliance ships a native CSI driver (csi/ in the source tree): dynamically provisioned PersistentVolumes backed by ZFS zvols, served over NVMe-oF/RDMA, with per-node host-NQN fencing. CSI volumes appear on NVMe-oF badged External with a live RDMA dot — the web never manages them, it only tells you the truth about them.

1. How it connects

controller pod ── ssh (pubkey, pinned host key) ──▶ greendot-csi user
                    gRPC over the session stdio        └─ forced command: greendotctl pipe
                                                           └─ the helper daemon socket
worker kernels ── NVMe/RDMA, port 4421 ────────────▶ dedicated CSI nvmet port

The cluster holds no root credential. The SSH login is the packaged greendot-csi user; its authorized_keys entry forces greendotctl pipe (with restrict), so the key can only speak the helper's typed protocol — every request is re-validated by the daemon's allowlist, exactly as greendot's own web UI is. The controller always verifies the box's SSH host key against a pinned known_hosts.

2. Box-side setup

# parent dataset for CSI volumes
zfs create tank/csi
# trust the controller's public key, pipe-only
install -d -o greendot-csi -g greendot-csi -m 700 /var/lib/greendotrdma/csi/.ssh
echo 'command="/usr/libexec/greendotrdma/greendotctl pipe",restrict ssh-ed25519 AAAA…' \
  > /var/lib/greendotrdma/csi/.ssh/authorized_keys

3. Cluster-side setup

kubectl -n kube-system create secret generic greendot-csi-ssh --from-file=id_ed25519=…
ssh-keyscan -H STORAGE_HOST | kubectl -n kube-system create configmap \
  greendot-csi-known-hosts --from-file=known_hosts=/dev/stdin
kubectl apply -f csi/deploy/    # edit controller.yaml's addresses first

Each worker needs the fabric module loaded (modprobe nvme-rdma, or nvme-tcp for TCP; persist via /etc/modules-load.d). No nvme-cli is required on workers — the node plugin writes /dev/nvme-fabrics directly. Note the transport is whatever the driver is configured with: rdma serves RDMA, tcp serves TCP — nothing "falls back" silently, and the dot on the Exports page shows which one initiators actually use.

4. Fencing — why RWO is safe here

Every volume is exported closed (allow_any_host=0, empty ACL). Attaching a pod grants exactly that node's host NQN; detaching runs a three-step fence on the target: revoke the ACL, unlink the subsystem from the port — which the kernel answers by deleting the node's live controllers — then relink. The fenced node's reconnect is rejected with DNR, so a rescheduled RWO pod can never leave two nodes writing the same block device, even when the old node is unreachable.

5. Snapshots and expansion

CSI snapshots are native ZFS snapshots of the volume's zvol; volumes can be cloned from them, and both online expansion halves work (the target grows the zvol and revalidates the namespace; the node grows the filesystem). greendot's own scheduled snapshot policies coexist — same COW objects, different names.

6. Using democratic-csi instead

democratic-csi's zfs-generic-nvmeof driver also works against this box, with trade-offs to understand:

  • It drives the box over SSH as root (or sudo — which for its stdin-fed nvmetcli and zfs invocations is root-equivalent), bypassing greendot's helper and its typed allowlist entirely, and it does not verify the SSH host key.
  • It needs nvmetcli on the box, which Ubuntu has never packaged — you install it from source or pip. (greendot itself needs no nvmetcli: the helper writes configfs directly.)
  • Its example config ships allow_any_host: 1 — no fencing. Lock each subsystem to the consuming node's NQN if you use it for RWO volumes.
  • NVMe-oF coexistence is safe (greendot only reconciles its own NQN prefix; foreign subsystems show as External). Do not run its iSCSI driver here: greendot applies iSCSI via targetctl restore, which clobbers targetcli-created targets on the next reconcile.
